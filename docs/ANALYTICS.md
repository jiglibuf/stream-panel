# Аналитика: откуда берутся сводки и какую локальную модель брать

Документ отвечает на два вопроса: как устроен модуль аналитики и какую локальную
модель выбрать на машине с 6 ГиБ видеопамяти, которая делит карту с игрой.

## 1. Что такое модуль аналитики

Модуль аналитики — это часть RedZone: он превращает сухой снимок матча в короткую
фразу для зрителя и кладёт её в тикер поверх карты.

```
Dota 2 (клиент шлёт GSI) ──HTTP POST──► сервис аналитики (:53000)
                                            │
                    детерминированные факты ◄┘  (покупка предмета + её тайминг)
                                            │
                              референс OpenDota (медиана по герою и предмету)
                                            │
                              локальная модель формулирует ОДНУ фразу
                                            │
                    тикер в OBS: «Phase Boots на 8:12 — на 47 с раньше, 320 игр»
```

Пример итоговой строки тикера:

> Omniknight: Phase Boots на 8:12 — на 47 с раньше среднего — медиана 8:59 — 320 игр

Ключевой принцип: **модель ничего не считает.** Все числа (время покупки, медиана,
отклонение, доля, объём выборки) считает детерминированный код из данных матча и
референса. Локальная модель только облекает готовый факт в одну фразу. Текст модели
принимается, только если **каждое число в нём есть среди чисел факта** и длина не
превышает 220 знаков; иначе берётся шаблон. Так исключены выдуманные числа в эфире.

## 2. Откуда данные: Game State Integration

Данные приходят официальным механизмом Valve — **Game State Integration (GSI)**.
Клиент Dota 2 сам отправляет HTTP POST с JSON-снимком матча. Никакого чтения памяти
и обхода античита нет: это тот же механизм, которым пользуются официальные
трансляции.

- Клиент шлёт снимок **по изменению, примерно до 10 раз в секунду**, на адрес службы
  аналитики, порт **53000**.
- Канал различается **токеном** в конфиге клиента: один канал — одно лобби (один
  аккаунт, один клиент). Ники игроков GSI не отдаёт, поэтому привязка идёт по токену.
- В режиме зрителя GSI отдаёт данные **по всем 10 игрокам** (при игре — только по
  своему герою), поэтому аналитика работает и на наблюдаемых матчах.
- Снимок — это «сейчас»: любые графики строятся накоплением выборок в SQLite
  (шаг задаётся параметром `sample_interval`, по умолчанию 10 секунд игрового
  времени).

Что приходит: счёт и фаза, драфт, по каждому игроку герой/уровень/K-D-A/нетворс/
GPM-XPM/предметы/байбек/респаун, Рошан и торментор, наблюдатели, башни/раксы/трон,
координаты героев. Combat-лога и чата GSI не даёт и не будет.

## 3. Установка

Модуль аналитики живёт **отдельным репозиторием** и подключается к RedZone как
внешний сервис: **https://github.com/jiglibuf/dota-analytics**

Установка коротко (подробности — в README самого репозитория):

```bash
git clone https://github.com/jiglibuf/dota-analytics.git
cd dota-analytics
uv venv .venv && uv pip install --python .venv/bin/python aiohttp
./scripts/run.sh start                 # служба на 127.0.0.1:53000, конфиг data/config.json
python tools/install_gsi_cfg.py --list # каналы, токены и куда ставятся cfg-файлы
python tools/install_gsi_cfg.py        # разложить cfg-файлы всех каналов
```

`tools/install_gsi_cfg.py` кладёт конфиги в каталог клиента Dota 2
(`.../dota 2 beta/game/dota/cfg/gamestate_integration/gamestate_integration_<канал>.cfg`).
Клиент читает этот каталог при запуске — **после установки Dota 2 надо перезапустить**.

Токены каналов и токен чтения генерируются сервисом при первом запуске в
`data/config.json` (в репозиторий не попадает). Шаблон структуры — `data/config.example.json`.

Ручки сервиса: `/healthz`, `/api/state`, `/api/history`, `/api/matches`,
`/api/analyst`, `/api/positions`, `/api/heatmap`, `/ws`, `/overlay`, `/overview`.
Для OBS тикер берётся из `/overlay/ticker.html?channel=<канал>` (полоса 1984×60 на
большой карте и 512×90 на миниатюре).

## 4. Как это держится в памяти

Сервис аналитики — маленький: **~42 МиБ ОЗУ и ~1 % одного ядра** в покое (замер
2026-10-05, `ps -o pid,rss,%cpu` и `systemctl --user show -p MemoryCurrent`; в журнале
OBS видно, что сводки строятся строго последовательно, один рабочий поток, — чтобы
модель не занимала видеопамять дважды).

Всю цену платит **локальная модель**, которая держится в видеопамяти. Ей и посвящён
остальной документ.

## 5. Таблица локальных моделей (замеры 2026-10-05)

Модели работают через Ollama на GPU (CUDA, GTX 1660 6 ГиБ). Замеры сняты так:

```bash
docker exec ollama ollama list                 # список и размер на диске
docker exec ollama ollama ps                   # резидентный размер, доля GPU/CPU, контекст
nvidia-smi --query-gpu=memory.used --format=csv,noheader   # до и во время загрузки модели
curl -s http://127.0.0.1:11434/api/chat -H 'Content-Type: application/json' -d @request.json
# в ответе: load_duration, eval_count, eval_duration → токены/с, а также total_duration (задержка)
```

Контекст по умолчанию в контейнере — `OLLAMA_CONTEXT_LENGTH=32768`. Запрос на сводку
идёт как в бою: `think=false`, `temperature=0.2`, `num_predict=96`, `keep_alive=30m`.

| Модель | Размер на диске | VRAM резидентно | Целиком в GPU | Скорость генерации | Холодный старт | Вердикт для этой машины |
|---|---|---|---|---|---|---|
| `gemma3:4b` | 3,3 ГБ | **+4,0 ГиБ** | да, 100 % | 55 ток/с | 17,5 с | **лучший выбор, когда игра не запущена**: сводка за 0,50 с |
| `qwen3:4b` (контекст 32768) | 2,5 ГБ | +4,3 ГиБ | нет, 20 % считает CPU | 28,5 ток/с | 22,3 с | на грани: медленнее и отбирает больше памяти |
| `qwen3:4b` (контекст 8192) | 2,5 ГБ | +3,2 ГиБ | да, 100 % | 54,4 ток/с | 2,1 с | хорошо, если нужны «рассуждения» qwen |
| `qwen3:1.7b` | 1,36 ГБ | +3,1 ГиБ | да, 100 % | 106 ток/с | 8,1 с | быстрая, но контекст 32768 раздувает VRAM |
| `gemma3:1b` | 0,82 ГБ | **+1,0 ГиБ** | да, 100 % | 119 ток/с | 2,3 с | **выбор, когда запущена игра** |

## 6. Прямой ответ: какую модель брать

**Если игра не запущена** (только эфир и аналитика):

- **`gemma3:4b`** — лучший выбор: отвечает за **0,50 с**, целиком в GPU, +4,0 ГиБ VRAM.
- `qwen3:4b` берите, только если нужны именно его рассуждения, и тогда **сократите
  контекст до 8192** — так он тоже уходит целиком в GPU и ускоряется с 28,5 до
  54,4 ток/с (см. §7).

**Если Dota 2 запущена** (карта делится с игрой):

- **`gemma3:1b`** — **+1,0 ГиБ VRAM**, 119 ток/с, сводка за **0,23 с**. Карте остаётся
  около 4,9 ГиБ — этого достаточно игре. Односложные сводки по факту она строит
  корректно (проверено: все числа берёт из факта).
- Ещё экономнее — `qwen3:0.6b` (0,52 ГБ) или `gemma3:270m` (0,29 ГБ).
- Модель на 4 ГиБ рядом с игрой **не держите**: она выдавливает игру из 6 ГиБ, и это
  как раз причина просадки FPS (разбор — `docs/PERFORMANCE.md`).

**Режим вообще без модели** — есть, и он полностью рабочий:

- Сводку собирает шаблон из тех же чисел факта (`source: "шаблон"`): «Omniknight:
  Phase Boots — на 8:12 — на 47 с раньше среднего — медиана 8:59 — 320 игр —
  источник OpenDota». Те же цифры, без формулировок.
- Стоимость: **0 МиБ VRAM, 0 мс задержки** — модель не запускается вообще.
- Включить: просто **не держать Ollama запущенной**. Если модель не ответила за
  `timeout` (по умолчанию 20 с), сервис сам подставит шаблон и напишет в лог причину;
  в тикере у сводки честно показывается бейдж источника — `qwen` или `шаблон`.
- Это разумный режим для игры: включайте модель только на «разговорных» отрезках,
  когда FPS не критичен.

## 7. Как переключить модель и контекст

- **Модель.** По умолчанию `qwen3:4b` (адрес `http://127.0.0.1:11434`). Модель
  задаётся там, где создаётся рассказчик, в `dota_gsi/server.py` (`Narrator()`), —
  поменяйте имя модели на выбранное из §5. Блок `analyst.narrator` в
  `data/config.json` документирует те же параметры (модель, адрес, таймаут,
  предельная длина фразы) для ориентира.
- **Контекст** — главный рычаг видеопамяти. В контейнере Ollama он один на всех:
  `OLLAMA_CONTEXT_LENGTH`. Уменьшение с 32768 до 8192 делает `qwen3:4b` полностью
  GPU-шным и вдвое быстрым:

  | Контекст | Резидентный размер | Сколько в GPU | Скорость | VRAM-прирост |
  |---|---|---|---|---|
  | 32768 | 5,4 ГБ | 80 % | 28,5 ток/с | +4,3 ГиБ |
  | 8192 | 3,3 ГБ | 100 % | 54,4 ток/с | +3,2 ГиБ |

  Правьте `OLLAMA_CONTEXT_LENGTH` в `docker-compose.yml` контейнера Ollama и
  перезапускайте контейнер.
- **Одна модель за раз.** `OLLAMA_MAX_LOADED_MODELS=1` и `OLLAMA_NUM_PARALLEL=1` уже
  выставлены: на 6 ГиБ две модели не уживаются, Ollama вытесняла бы их по кругу.
  Сводки для этого и строятся последовательно, в один поток.
